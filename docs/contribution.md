# 贡献指南

状态：初始协作约定，将随社区形成而调整。

MorphoJudge 欢迎 AI 工程师、软件开发者、安全研究人员和架构师参与。贡献可以从问题和证据开始，不要求先提交代码。

## 当前适合参与的工作

- 提供经过脱敏、可公开的 AI Coding 审查案例。
- 改进问题定义，指出不成立的假设和未覆盖的边界。
- 讨论证据格式、行为分类、报告表达与本地数据边界。
- 提供可复现的误报、漏报和提示注入样例。
- 改进文档、翻译和原创视觉素材。

## 从问题到代码

1. 分析问题：说明用户场景、预期行为、实际困难与影响。
2. 设计方案：比较可行路径，说明边界、成本和验证方法。
3. 形成公开文档：将可讨论的设计整理到 `docs/`，注明草案状态。
4. 拆解 Issue：为独立交付物定义范围、依赖与验收条件。
5. 开发代码：在约定范围内实现，完成相关验证并提交 PR。

文档纠错可以直接提交小型 PR。新增架构或能力应先建立可审阅设计。初始任务见 [Issue 草案](issues.md)，现阶段无需为了占位而生成分析器或模型接口代码。

## Issue 建议内容

- 问题与用户场景。
- 预期结果及当前可观察行为。
- 可公开的最小示例和复现条件。
- 建议范围、不包含的内容及关联文档。
- 验收条件、可能的失败情况与待讨论点。

仓库发布到 GitHub 后，可按草案创建实际 Issues；目前文档中的任务编号只在本仓库内引用。

## PR 建议内容

说明解决的问题、最终行为、关联设计或 Issue、验证结果及仍存在的限制。实现变更需要与风险相称的测试；纯文档修改检查内容准确性、链接和状态标记即可。

不要把没有运行过的 Demo、没有适配的模型或未验证的扫描能力写成已支持功能。AI 辅助生成的内容同样由提交者复核其正确性与授权来源。

## 公开与私有资料

| 可以公开 | 仅保存在本地 |
| --- | --- |
| 项目愿景、需求、技术设计、架构草案 | AI 聊天记录、私人开发计划 |
| Issue、Open Problems、已核实的实验结论 | 技术推演、原始实验记录、失败尝试、临时想法 |
| 开源代码、脱敏样例、可复现验证方法 | 私有代码、真实凭据、敏感报告 |

本地资料放入 `PRIVATE/`。`.gitignore` 也排除了 `*.private.md`、`ai-chat/`、`personal-plan/`、`experiments/`。不要通过强制添加绕过规则。

提交前检查暂存差异；忽略规则不会自动移除已经被跟踪的文件。若发现误提交，应先停止传播并按具体内容处理，不能只补一条忽略规则。

私人实验可以整理为可复现的公开设计或结果，但应移除聊天原文、私人计划和敏感信息，并清楚区分结论与假设。

## 社区沟通

围绕可验证的技术问题讨论，尊重不同经验，不做人身攻击。分歧应记录假设、证据和复现方法。初期由发起人维护文档与合并流程，治理方式随实际贡献者增长公开讨论。

当前尚未建立专用安全报告渠道。不要在公开 Issue 中提交真实密钥、未授权的私有代码或第三方未公开漏洞细节；发布仓库时应补充可用的私下报告渠道。

## 许可证与素材

提交者应有权贡献相应内容。本仓库采用 MIT License；第三方依赖、模型和图片需要分别记录来源与许可证。不要将可下载的模型自动标记为符合任意开源定义。
