# 问题定义

状态：问题分析草案。经验描述需要通过公开案例与评测进一步验证。

## 开发流程发生了什么变化

从“人设计、编码、测试、审核”，到“AI 理解需求、生成并修改代码、运行测试，人验证结果”，工作量并没有简单消失，而是重新分布。

AI 一次生成的变更可能超过开发者短时间内可以理解的范围。程序可以运行、测试可以通过，但这不足以回答设计是否合理、行为是否符合预期。

## 核心痛点与可观察结果

| 痛点 | 开发者的问题 | 希望报告提供的内容 |
| --- | --- | --- |
| 代码成为理解上的黑盒 | 为什么改这里？影响哪里？ | 变更摘要、结构关系及来源 |
| 生成快于理解 | 先看哪些代码最有价值？ | 按证据与影响组织的关注项 |
| 引入非预期行为 | 为什么新增网络访问或系统命令？ | 行为位置、参数线索、与基线的差异 |
| 团队难以建立交付依据 | 哪些已验证？哪些仍未知？ | 比较范围、检查结果、遗漏与人工复核项 |

“开发 80%、审核 20%”与“生成 20%、理解 80%”仅用于说明发起人的体验变化，不应作为对行业的量化结论。

## 行为不等于风险结论

网络访问、外部 API、文件操作、Shell 执行和权限变更都有合理用途。是否构成风险取决于需求、输入来源、运行环境和权限边界。

例如，新增 HTTP 请求只能证明代码包含相关调用；仅凭该调用不能声称敏感数据已经外传。报告应展示传入数据的可见来源，并说明尚未验证的路径。

## 为什么采用本地方案

私有代码、知识产权与环境限制可能不允许云端上传；大型仓库的传输与推理成本也需要控制。本地分析可以提供更清晰的数据边界，但本地模型同样可能幻觉、误判或被仓库内容中的提示注入影响。

可信判断需要可复核证据、明确覆盖范围和人工验证，不能只依赖另一个模型给出“安全”评价。

## 需要收集的场景

- 一次多文件修改中，实际行为与任务要求出现偏差。
- 新依赖引入了来源变化或需要额外核实的安装行为。
- 权限逻辑调整通过现有测试，却改变访问边界。
- 合法网络请求被误报，或间接调用造成漏报。
- 大型仓库受本地硬件限制，必须进行有边界的增量分析。

贡献案例时只提交可公开的最小复现，说明预期行为、实际差异、审查难点与判定依据。不得上传私人代码或真实凭据。
