# 路线图

状态：阶段规划，不承诺发布日期。功能范围以 [PRD](PRD.md) 为准。

## 开发顺序

分析问题 → 设计方案 → 形成公开文档 → 拆解 Issue → 开发代码。

每次扩展能力前，都应先说明具体问题、边界、验证方法与维护成本。

## P0：建立问题与协作基础

- [x] 初始化 README、核心文档与目录骨架。
- [x] 明确公开资料与本地私有开发资料的边界。
- [x] 公开开放问题、贡献流程与初步 Issue 草案。
- [ ] 收集可公开的真实审查场景，并完成问题定义讨论。

进入下一阶段的依据：社区可以理解项目解决什么、暂不解决什么，以及如何提供有效案例。

## P1：确定最小方案

- [x] 选择首个分析语言与依赖生态（TypeScript/JavaScript Web fixture；详见 PRD 0.20）。
- [ ] 定义 Git 比较范围与特殊文件处理方式。
- [ ] 设计证据与报告字段，明确错误、遗漏和未知项。
- [ ] 确定首批行为规则及正例、反例。
- [ ] 验证一个本地模型与运行时的可行性及许可证（Ollama；任务 LLM-003）。
- [x] 形成 Web 工作台 + 本地分析服务的技术栈决策草案。
- [x] 建立 Web 原型 Docker 开发与生产预览构建，验证热更新、类型检查、健康检查和本机端口。
- [x] 按 PRD 0.3 接入软件关系示例原型：多栏联动、宏观网络、对应表、注释一致性与反向影响路径。
- [ ] 将真实代码解析结果接入同一关系契约，验证跨文件调用和分析盲区。
- [x] 将草案转化为边界清晰、有验收条件的内部任务规格；实际 GitHub Issues 仍待创建。

进入实现的依据：有可审阅设计、最小示例和验收条件，而不只是功能名称。相关草案见 [issues.md](issues.md)。

## P2：MorphoJudge v0.1

目标：Git 仓库 → 本地分析 → 可信审计报告。

- [ ] 提取新增、修改、删除文件及 Diff。
- [ ] 展示项目结构、支持范围内的模块关系与调用线索。
- [ ] 检查网络、外部 API、Shell、文件与权限相关行为。
- [ ] 识别首个生态的依赖新增、版本与来源变化。
- [ ] 生成带证据的本地模型解释和人工复核项。
- [ ] 提供可阅读报告与结构化输出。
- [ ] 提供可复现 Demo、实际运行命令与环境说明。

发布验收条件：

1. 示例仓库的每项发现可以定位到对应快照和代码位置。
2. 区分基线已有行为和新增变化，展示分析覆盖与失败项。
3. 在所选的最小规则样例集上评估误报与漏报，公开限制。
4. 断开外网后，在资源已经准备好的环境中完成基础分析与本地推理。
5. 模型不可用时仍能输出基础证据，并明确缺失的解释。
6. 验证目标仓库代码不会因分析而执行，仓库内指令不能驱动额外工具调用。

v0.1 不包括全语言支持、完整知识图谱、SaaS、企业控制台、自动修复与自动发布。

## P3：以证据推动扩展

- [ ] 建立公开评测集，研究误报、漏报与报告可用性。
- [ ] 根据实际需求增加语言和本地运行时。
- [ ] 探索增量索引、大型项目上下文选择与关系图。
- [ ] 在分析结果稳定后讨论 CI、IDE 和企业内部集成。

扩展优先级由真实案例、评测结果和维护者容量决定；研究方向不直接等同于承诺交付。
