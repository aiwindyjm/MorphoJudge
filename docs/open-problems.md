# Open Problems

状态：公开研究问题，尚未解决。

我们不希望用完整功能清单掩盖未知。以下问题值得开发者、AI 工程师、安全研究人员和架构师共同探索。

## OP-01：如何准确理解 AI 生成代码的意图？

代码显示实现，却不一定包含完整需求。模型可能把实现行为误当成设计意图。

研究方向：结合用户提供的需求、Diff 与代码证据，把“代码做了什么”和“为什么这样做”分别表达。

验证方式：建立带明确需求和人工标注的变更样例，评估事实准确率、意图推测偏差，以及能否主动报告缺失上下文。

## OP-02：如何降低大型项目分析成本？

全量扫描、重复推理和过长上下文会增加时间与资源成本；只看 Diff 又可能遗漏间接影响。

研究方向：增量索引、基于依赖关系选择上下文、可解释的缓存失效策略。

验证方式：在不同仓库规模上同时测量耗时、内存、重复分析成本与漏报变化，防止用牺牲覆盖换取漂亮的速度指标。

## OP-03：如何让小模型帮助理解百万级代码？

百万行仓库不能简单装进一次上下文。模型规模、上下文窗口和硬件资源都有限。

研究方向：分层摘要、符号检索、证据片段选择，以及把适合确定性分析的任务交给解析器。

验证方式：设计跨文件问题，比较检索命中、答案证据完整性与错误传播；同时记录模型版本和资源条件。不能将摘要生成成功等同于理解整个仓库。

## OP-04：如何跨语言建立统一代码知识图谱？

不同语言的模块、类型、动态调用与构建方式差异很大；过早统一可能丢失关键语义。

研究方向：先定义少量公共实体和带来源的关系，再允许语言特有扩展和未知边。

验证方式：用包含跨语言接口的最小仓库，检验关系是否能追溯、更新是否正确、无法解析的部分是否可见。

## OP-05：如何判断 AI 是否引入隐藏行为？

行为可能经过包装、动态加载、反射或依赖间接引入。发现某个 API 名称，既不能证明有恶意，也不能覆盖全部行为。

研究方向：基线对比、数据与调用线索、依赖来源、显式行为预期；更深入的执行分析需另行设计隔离边界，不属于 v0.1 默认范围。

验证方式：构建可安全公开的正例、正常用途反例与绕过样例，分别评估行为检出和风险判断。

## OP-06：如何减少误报？

大量低价值提示会消耗审查注意力。模型自报的置信度不应直接当作经过校准的概率。

研究方向：区分影响程度与证据可靠性、允许记录带理由的人工反馈、结合项目明确声明的行为预期。

验证方式：公开样例定义与人工判定过程，分别统计精确率和召回率，同时观察被压低优先级的真实问题。

## OP-07：如何防止仓库内容操纵分析过程？

注释、文档或字符串中可能包含针对模型的指令。部署在本地不会消除提示注入问题。

研究方向：隔离任务指令与仓库内容、限制模型职责、校验证据引用，不给解释模型执行仓库命令的权限。

验证方式：构造对抗样例，检查是否改变报告结论、生成无依据发现，或诱导越权读取与执行。

## 如何参与

讨论时引用 OP 编号，说明具体场景、假设、可公开样例、验证方法和仍未解决的部分。实验过程保存在本地私有目录；公开发布可复现方法与经过核实的结果，并保留负面结果和限制。

OP 编号是本文内部标识，不是已创建的 GitHub Issue 编号。协作流程见 [贡献指南](contribution.md)。
